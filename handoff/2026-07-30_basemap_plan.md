## 0. 検証結果（推測でなく実測）

### 道路が「ぐちゃぐちゃ」に見える原因 = 手選別による歯抜け

| | 現行 GEO.roads | 生データ osm_raw2.json（ローカル・2.5MB） |

| 描いている道 | **62本**（major1 / mid45 / minor16） | residential **904** / service **515** / footway **578** / tertiary 85 / unclassified 56 / secondary 22 / primary 8 / path 72 / steps 65 |
| 品質 | **31本が2点だけの切れ端**・総延長19km | 全網・ジオメトリ完備 |

`build_mapdata.py:316-331` が `CORE_BUS_NAMES` / `SOUTH_BRANCH_NAMES` 等の**名前の手選別リスト**で通し、リスト外は捨てている。周辺の生活道路が全部欠けるので、Googleマップの網目と見比べると「道が無い／千切れている」＝ぐちゃぐちゃに見える。**再構築に必要なデータは全てローカルに有り、追加取得は不要。**

## 1. フェーズ構成

### E-1: ベースマップのデータ再構築（研究不要・仕様確定済み）

1. **全道路クラスを取り込む**。名前選別を廃止し、class ベースに:
   - `major` = primary / secondary（バス通り=中山幹線1号線は現行どおり強調維持）
   - `mid` = tertiary / unclassified
   - `minor` = residential / living_street
   - `service` = service（細く・薄く）
   - `path` = footway / path / steps（点線・高ズームのみ）
2. **切れ端の根絶**: canvas矩形でポリラインを正しくクリップ（Cohen–Sutherland）。道は必ず画面端まで到達するか、OSM上の実際の行き止まりで終わる。中空に浮く端点を禁止
3. **信号の全数化**: `signals_raw.json` から canvas 内全数を取り込み。座標は投影のみ（手調整禁止）
4. パフォーマンス予算: 全網SVG化でDOMノードが増えるため、同一classは1つの `<path>` に統合（d属性連結）。目標=モバイルで初期描画 < 1.5s / パン・ズーム60fps維持

### E-2: 見やすさのスタイル + UX（調査ワークフローの統合結果で確定）

調査中（5視点並列: Google/Apple分解・イラスト地図実例・カートグラフィ定石・密集POI UX・現行実装監査）。統合結果の design_decisions を反映して確定する。想定領域:

- 図地関係（道路を明るく・地をやや濃く＝街区が自動的に浮かぶGoogle方式。建物ポリゴン無しで成立）
- 道路のcasing（縁取り）と幅の階層、classごとの出現ズーム
- 信号アイコンの控えめ化
- **方位コンパス**（この地図は46.4°回転しているので北表示は必須級）
- **現在地ボタン**（実座標地図になったのでGPSが初めて意味を持つ。精度サークル＋圏外時の挙動）
- 初期ズームのフィット、「ズームすると店名が出ます」の案内の磨き込み
- 手描きの可愛さ（クリーム&ブラウン/Yusei Magic）は**不可侵**。壊す提案は不採用
